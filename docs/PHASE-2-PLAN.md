## ส่วนที่ 2 — สภาพเว็บจริงตอนนี้ (ตรวจแล้ว ไม่ได้เดา)

### 2.1 เว็บตอนนี้ไม่มีสีแบรนด์เลย

`src/index.css` ใช้สีเทาล้วนทั้งหมด สังเกตจากค่าสีทุกตัวเป็นรูป `oklch(ตัวเลข 0 0)` — เลข `0` ตัวกลางคือ "ความอิ่มสี" ซึ่งเป็นศูนย์ แปลว่า**ไม่มีสีเลย เป็นเทาล้วน**

```
--primary: oklch(0.205 0 0);     ← ดำเทา ไม่ใช่สีแบรนด์
--destructive: oklch(0.577 0.245 27.325);  ← แดง (ตัวเดียวที่มีสี)
```

นี่เป็นค่าเริ่มต้นที่ติดมากับเทมเพลต ยังไม่เคยตั้งค่าสีของแบรนด์เลย

### ขั้นที่ 2 — ต่อสีแบรนด์เข้าระบบ (เสี่ยงปานกลาง แต่ผลชัดที่สุด)

**นี่คือขั้นที่ยากที่สุด และเป็นจุดที่ต้องตัดสินใจ**

ปัญหาคือมีชื่อตัวแปรสีอยู่ **สองชุดที่ไม่รู้จักกัน**

- `docs/brand/tokens.css` ใช้ชื่อ `--rl-primary`, `--rl-bg`, `--rl-text` …
- `src/index.css` ใช้ชื่อ `--primary`, `--background`, `--foreground` … (ชื่อของ shadcn ซึ่งคอมโพเนนต์ทุกตัวในเว็บเรียกใช้อยู่)

ถ้าเอา `tokens.css` ไปวางเฉยๆ **จะไม่มีอะไรเปลี่ยนเลย** เพราะไม่มีใครเรียกชื่อ `--rl-*`

**ทางแก้ที่แนะนำ: ต่อท่อ ไม่ใช่แทนที่**

ให้ตัวแปรของ shadcn ชี้ไปที่ตัวแปรของแบรนด์ แบบนี้

```css
:root {
  --primary: var(--rl-primary);
  --background: var(--rl-bg);
  --foreground: var(--rl-text);
  /* ...ทีละตัว... */
}
```

**ทำไมต้องทำแบบนี้:** คอมโพเนนต์ทุกตัวในเว็บ (ปุ่ม การ์ด ป้าย ช่องกรอก) เรียกชื่อ shadcn อยู่แล้วทั้งหมด ถ้าไปไล่แก้ทุกคอมโพเนนต์ให้เรียกชื่อใหม่ จะแตะไฟล์เป็นสิบและพังง่ายมาก แต่ถ้าต่อท่อที่จุดเดียว คอมโพเนนต์ทั้งหมดเปลี่ยนสีพร้อมกันโดยไม่ต้องแตะเลยสักตัว

**ข้อควรระวัง:** โหมดมืดต้องต่อท่อแยกอีกชุดใน `.dark` ถ้าลืม โหมดมืดจะค้างเป็นเทาล้วนอยู่อย่างเดิมและไม่มีอะไรฟ้อง

**ทดสอบ:**
- `npm run test` — มีเทสต์คุม `App.tsx` อยู่ ~458 บรรทัด
- `python docs/brand/verify-contrast.py` — ยืนยันว่าสีที่ใช้จริงยังอ่านออก
- เปิดเว็บสลับโหมดมืด/สว่างดูด้วยตา

## ส่วนที่ 4 — ช่องโหว่ที่ทำให้ CI ขึ้นกากบาทแดง

### เกิดอะไรขึ้น

CI ขึ้น ❌ **ไม่ใช่เพราะงานแบรนด์** งานแบรนด์แตะแค่ `docs/` ไม่ได้แตะโค้ดหรือ dependency เลย

สาเหตุคือขั้นตอน `audit:prod` ใน `.github/workflows/ci.yml` ตรวจเจอช่องโหว่ระดับ high:

```
nanoid  <3.3.17
Severity: high
nanoid: custom generators can loop indefinitely when size is zero
1 high severity vulnerability
```

CI ตั้งไว้ให้ล้มทันทีเมื่อเจอระดับ high ดังนั้น**ตั้งแต่วันที่ประกาศช่องโหว่นี้ออกมา CI จะแดงทุก commit** ไม่ว่า commit นั้นจะแก้อะไร

### ต้นตอ

`nanoid` ไม่ใช่ของที่ติดตั้งเอง แต่ติดมาเป็นทอดๆ

```
rubriclens-ai
└─ shadcn 4.16.1
   └─ postcss 8.5.25
      └─ nanoid 3.3.16   ← ตัวที่มีปัญหา
```

### ประเด็นที่ลึกกว่านั้น

`shadcn` ถูกประกาศไว้ใน `dependencies` (ของที่ถือว่าจำเป็นตอนเว็บทำงานจริง) แต่ความจริงแล้ว**มันเป็นแค่เครื่องมือบรรทัดคำสั่งไว้ก๊อปโค้ดคอมโพเนนต์ตอนพัฒนา** เว็บที่ผู้ใช้เปิดไม่ได้ต้องใช้มัน

ตรวจแล้วพบว่าทั้งโปรเจกต์เรียกใช้ `shadcn` แค่จุดเดียว:

```
src/index.css:3:  @import "shadcn/tailwind.css";
```

ซึ่งเป็นการอ่าน **ตอน build** เท่านั้น พอ build เสร็จ CSS ถูกฝังลงไฟล์ผลลัพธ์แล้ว ตัวแพ็กเกจไม่ได้ถูกส่งขึ้นเว็บด้วย

### ทางเลือกในการแก้ (ยังไม่ได้ทำ)

| # | วิธี | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **1** | **ย้าย `shadcn` ไป `devDependencies`** | แก้ตรงต้นเหตุ — ประกาศให้ตรงความจริงว่ามันเป็นเครื่องมือตอนพัฒนา แล้ว `audit:prod` จะเลิกสนใจมันถาวร ไม่ต้องมาไล่แก้ทุกครั้งที่ postcss มีข่าว | ต้องยืนยันว่า `npm run build` ยังผ่าน (ควรผ่าน เพราะ CI ติดตั้งทั้งสองกลุ่มอยู่แล้ว) |
| **2** | `npm audit fix` | เร็ว ตรงจุด ดัน nanoid ขึ้น 3.3.17 | ไม่แก้เรื่อง `shadcn` อยู่ผิดกลุ่ม รอบหน้าที่ postcss มีช่องโหว่ใหม่ก็แดงอีก |
| **3** | ใส่ `overrides` ใน `package.json` บังคับเวอร์ชัน nanoid | คุมได้แน่นอนว่าใช้เวอร์ชันไหน | ต้องมาดูแลเองตลอดไป และอาจขัดกับเวอร์ชันที่ postcss ต้องการในอนาคต |
| **4** | ผ่อนเกณฑ์ CI เป็น `--audit-level=critical` | CI เขียวทันที | **ไม่แนะนำ** — เท่ากับปิดตาไม่ดูช่องโหว่ระดับ high ทั้งหมด แลกความสบายใจระยะสั้นกับความเสี่ยงระยะยาว |
| **5** | ปล่อยไว้ | ไม่ต้องทำอะไร | CI แดงค้างตลอด นานไปจะชินและเลิกดู ทำให้วันที่พังจริงจะไม่มีใครสังเกต |

**คำแนะนำ: ทำข้อ 1 ก่อน แล้วรัน `npm audit --omit=dev` ซ้ำเพื่อยืนยันว่าเงียบจริง** ถ้ายังไม่หายค่อยเสริมข้อ 2

**หมายเหตุความเสี่ยงจริง:** ช่องโหว่นี้เกิดเมื่อเรียก `nanoid` ด้วยขนาดเท่ากับศูนย์ ซึ่งเป็นการเรียกที่โค้ดในโปรเจกต์นี้ไม่ได้ทำ และตัว nanoid ก็ไม่ได้ถูกส่งไปรันบนเบราว์เซอร์ผู้ใช้ **เว็บที่รันอยู่ตอนนี้จึงไม่ได้อยู่ในอันตราย** — ที่ต้องแก้คือเพื่อให้ CI กลับมาเชื่อถือได้ ไม่ใช่เพราะเว็บกำลังถูกเจาะ

## ส่วนที่ 5 — เคลียร์ไฟล์ให้สะอาด

### 5.1 ไฟล์ที่ยังไม่ได้เข้า git และควรตัดสินใจ

| ของ | สภาพ | ข้อเสนอ |
|---|---|---|
| `.claude/` | ยังไม่ได้เข้า git | ใส่ `.gitignore` — เป็นค่าตั้งเครื่องมือส่วนตัว ไม่ควรอยู่ใน repo สาธารณะ |
| `correct/` | ยังไม่ได้เข้า git มี 2 ไฟล์ (~58 KB) เป็นบันทึกรีวิว prompt | ถ้าเป็นบันทึกที่อยากเก็บ → ย้ายเข้า `docs/` แล้ว commit ให้เรียบร้อย ถ้าเป็นของชั่วคราว → ใส่ `.gitignore` **อย่าปล่อยค้างแบบนี้** เพราะทุกครั้งที่เปิด `git status` จะรก จนวันหนึ่งมีไฟล์สำคัญโผล่มาแล้วมองข้าม |

### 5.2 ปัญหาปลายบรรทัดของ `docs/architecture.md`

`git status` ขึ้นว่าไฟล์นี้ถูกแก้ 227 บรรทัด แต่**เนื้อหาเหมือนเดิมทุกตัวอักษร** ต่างแค่อักขระจบบรรทัด (Windows ใช้ CRLF, git เก็บเป็น LF)

นี่ไม่ใช่ของที่ผมแก้ และไม่ควรปล่อยไว้ เพราะ diff ปลอมแบบนี้จะบังการแก้ของจริงที่ปนมาทีหลัง

**ทางแก้ถาวร:** เพิ่มไฟล์ `.gitattributes` ที่รากโปรเจกต์

```
* text=auto eol=lf
*.png binary
*.svg text eol=lf
```

แล้วรัน `git add --renormalize .` หนึ่งครั้ง จบปัญหาถาวรทั้งโปรเจกต์

### 5.3 ไฟล์ที่ลบได้หลังเฟส 2 เสร็จ

- `public/icons.svg` — ไม่มีใครเรียกใช้ ลบได้เลยตอนนี้
- `docs/brand/logo/_retired/` — รอจนเฟส 2 เสร็จและพอใจกับมาสคอตใหม่ค่อยลบ

## ส่วนที่ 6 — ลำดับที่แนะนำ

ทำจากเสี่ยงน้อยไปมาก แต่ละข้อ = 1 commit แยกกัน

1. เพิ่ม `.gitattributes` + `git add --renormalize .` → เคลียร์ diff ปลอม
2. ใส่ `.claude/` ใน `.gitignore` + จัดการ `correct/`
3. ย้าย `shadcn` ไป `devDependencies` → CI กลับมาเขียว
4. เปลี่ยน favicon + og.png + theme-color + ลบ `icons.svg`

## ส่วนที่ 7 — สิ่งที่ยังไม่ได้ตรวจ และอาจพลาด

ระบุไว้ตรงๆ เพื่อไม่ให้เข้าใจว่าทุกอย่างถูกยืนยันแล้ว
